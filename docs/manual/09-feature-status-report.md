**Volume 09 of the documentation package** · Rev. Fr. Moses Orshio Adasu University, Makurdi · Directorate of ICT · Version 1.0 · 26 September 2026 · as at commit `8c2b6fa` on `main`

This is the control document of the package. It states, feature by feature, what the MOAUM Unified University Portal does today, what it half does, what exists in the schema or the API without a screen, what is a placeholder, and what is not there at all. Every other volume defers to this one: where a manual describes a screen and this report marks the feature **PARTIALLY IMPLEMENTED** or **NOT IMPLEMENTED**, the report is right and the screen's own words are wrong. Nothing unfinished is presented here as complete, and nothing here was changed in the portal to make it so — this is a documentation exercise only.

## 1 Method

### 1.1 What was checked for every feature

The status of each feature was established by an audit of the repository at commit `8c2b6fa` on `main`, the database schema produced by applying every migration `V001`–`V263` to a local PostgreSQL cluster, and the frontend as built. The audit was recorded in seven module dossiers (A–G, filed with the package in `docs/manual/audit/`), and every row of every dossier's implementation-status table is carried into §3 of this report. For each feature five layers were checked and a feature is **IMPLEMENTED** only when all five hold:

| Layer | What was checked | Where the evidence comes from |
|---|---|---|
| **UI** | A page under `frontend/src/app/**` renders the feature; its controls are wired (`onClick`, form submit, `fetch` to the BFF); the office's menu (`frontend/src/lib/menus.ts`) or an in-page link reaches it | `routes.md`, `menus.md` (generated by `tools/parse_front.py`), the TSX files |
| **Backend** | A controller under `api/src/main/java/ng/edu/moaum/portal/**` exposes the endpoint the page calls; the service or SQL function performs the act rather than answering a stub `202` | `api.md` / `api.json` (generated by `tools/parse_api.py`), the Java and SQL sources |
| **Permission** | The endpoint's `@PreAuthorize` guard names the office whose menu offers the screen; where a scope applies (department, faculty, level, course) the controller binds it | `generated/permission-matrix.md`, the guard constants (*04 Role & Permission Matrix*, §8) |
| **Workflow** | Every state the CHECK constraint allows has a writer; every transition the screen promises exists in a function or trigger; notices the screen or migration promises are actually queued (`platform.queue_notice`) | `constraints.psv`, `functions.psv`, `triggers.psv`, the migrations |
| **Database** | The tables and columns the feature needs exist, are attached to the audit spine or exempted with a reason, and are written by something other than `demo.sql` or the tests | `tables.psv`, `columns.psv`, `audit.unattached()`, row counts on the local cluster |

Where a layer was missing the feature was marked down, never up. Text on a screen ("verified nightly", "the student is told", "rate-limited") counted for nothing unless the code behind it was found.

### 1.2 The five statuses

| Status | Meaning | Typical evidence |
|---|---|---|
| **IMPLEMENTED** | All five layers hold. The feature can be used from its screen by the office named, the rule is enforced, the data is written and audited. Qualifications (a stale caption, a missing export, a hard-coded default) are recorded in *Notes* and in §4, not in the status | A page, a guarded endpoint, a function, and where promised a notice |
| **PARTIALLY IMPLEMENTED** | The feature works in part: typically a backend endpoint with no screen ("backend only"), a screen whose office is refused by the guard, a flow with one unreachable stage, or code that is complete but not deployed | An endpoint with no `fetch` in `frontend/src`; a menu item whose calls answer 403 |
| **CONFIGURED BUT UNUSED** | A table, column, state value or endpoint exists in the schema or the API and nothing in the application writes or calls it. Safe to leave; not to be relied on in reports | A CHECK value with no `UPDATE … SET state = '…'` anywhere in `db/` or `api/` |
| **PLACEHOLDER** | A page, tile, button or endpoint that renders or answers but performs nothing: a `202` that sends nothing, a button with no handler, a card that prints "—" or "NOT YET SERVED", a page of static text | `ResultsController.java:181-188`; `Chain.tsx:91`; `Self.tsx:87-89` |
| **NOT IMPLEMENTED** | Nothing exists for the feature in code or schema, or the only trace is a comment or a hint string. Includes features a screen text promises ("Overload is reported to the Dean") and features the University asked about that the portal does not have (a CBT test engine) | No code found; a `HINT` string only |

Two conventions apply throughout. Where a dossier used a compound status ("IMPLEMENTED (code), NOT DEPLOYED"; "IMPLEMENTED but UNUSED BY THE UI"; "RECORD ONLY") it is mapped to the nearest of the five above and the qualification is kept in *Notes*: undeployed code is **PARTIALLY IMPLEMENTED**; an endpoint no screen calls is **PARTIALLY IMPLEMENTED** when a screen should call it and **CONFIGURED BUT UNUSED** when it has been superseded; a recorded-but-not-executed payout is **PARTIALLY IMPLEMENTED**. And "by design" gaps (the applicant cannot type O'Level grades; Deans cannot keep a copy of a return) keep the status **NOT IMPLEMENTED** with the design note beside it, so that nobody reads the table and expects the button.

### 1.3 Evidence and sources

Every row cites its evidence as `file:line` or `file:range` in the repository (Java under `api/src/main/java/ng/edu/moaum/portal/…`, TSX under `frontend/src/app/…`, SQL as `db/Vnnn` with a line where the dossier gave one), or as a SQL function or trigger name. A citation such as `ApplicantsController.java:455` is the line of the handler in question at commit `8c2b6fa`; later commits will move it. Where a finding was made by the generated inventories rather than by reading the file, the inventory is cited (`menus.md`, `routes.md`). Where the dossier said something the code contradicted on re-reading, the code wins and §1.4 says so. Where a claim could not be verified it is written "not verified".

The sources, in order of authority:

1. The repository at `8c2b6fa` and the schema produced by its migrations.
2. The seven audit dossiers (`docs/manual/audit/A-platform-identity.md` … `G-services-documents.md`), each with a §13 *Implementation status* table per module and a §12 *Security notes* section.
3. The generated inventories (`tools/out/api.md`, `routes.md`, `menus.md`, `generated/permission-matrix.md`, `generated/database-reference.md`), regenerable with the scripts in `docs/manual/tools/`.
4. The consolidated findings already published in the other volumes — *01* §7–9, *02* §8, *03* §5.14 and §11, *04* §4, *06* §13, *07* §4, *08* §4.5 — which this report merges and does not contradict.

### 1.4 Counting rules and corrections to the dossiers

- **One row per feature, de-duplicated across dossiers.** A feature two dossiers both recorded (the Bursar dashboard, the intake run, the hostel clearance unit) appears once, under the module that owns the code, with a cross-reference. Rows a dossier marked "other group" are not counted.
- **Screen-audit annexes are not status rows.** Dossier F's Annexes A and B (a control-by-control reading of every finance, HR and student-money page) contributed their *Unfinished, hard-coded or inconsistent* findings to §4.5 and to *Notes*, not to the count.
- **Two corrections.** Re-reading the frontend for *07 API Reference* found callers for two endpoints the dossiers had listed as backend-only: `POST /api/v1/student/intake/{session}/{year}` is called by the Admissions page (`frontend/src/app/admissions/Admissions.tsx:49`), and `GET/POST /api/v1/research/grants` (and `POST …/{id}/state`) are read and written by *Research › My Projects* (`/research/projects`). Both are counted **IMPLEMENTED** here; neither appears in §4.2. The research-grants page has a different defect — it is on the Lecturer's and Dean's menus while the guard refuses those offices (§4.3).
- **Security findings are not counted twice.** A missing rate limit or an unbound read is a row in §5 with a severity; it appears in §3 only where it is also a feature gap (for example, "Held scripts — ownership check").
- **Bugs are notes.** A control that misbehaves on an otherwise working screen (`ReconcileLedger.tsx:45` toasting an error on every successful load; `Hanging.tsx:74` showing nothing on failure) is recorded in *Notes* and in §4.5; the feature keeps its status.

### 2.1 Counts by status

The matrix in §3 has **490 feature rows in 49 module groups**, drawn from 47 API modules, 919 endpoints, 331 tables and the menus of 34 offices.

| Status | Rows | Share |
|---|---|---|
| **IMPLEMENTED** | 353 | 72.0 % |

Read the 66 **NOT IMPLEMENTED** rows with care. Eleven are missing notifications on otherwise working flows (registration approval, transfers, publication, College decisions, LMS, new PG applications, unanswered requests, due returns). Eighteen are administration, export or verification surfaces for data the portal already holds (a grading-policy screen, deferment settings, College configuration, a Senate-schedule print, examiner PDFs, payslip and movement letters, three verification pages, the search-log reader). Six are security controls (rate limits, the chain job, the held-script ownership check, document signing — §5). Two are recorded design decisions kept so nobody looks for the button (the applicant cannot type O'Level grades; Deans cannot keep a copy of a return). The remaining twenty-nine are functional gaps, the largest of which head the top-25 list below.

By module group (§3.1–§3.49), the groups with the highest share of non-IMPLEMENTED rows are Help & Requests (2 of 8 implemented), the CBT question bank (1 of 4), Human resources (6 of 12), Course registration approvals (6 of 12), the University Health Services clinic (4 of 8), SIWES (2 of 4), Result queries (2 of 4) and Clearance (3 of 6). The groups with the lowest are the Staff module (4 of 4), Hostel (18 of 20), Digital documents (19 of 21), ICT Support Desk (13 of 14), the Student portal (16 of 17), Finance (17 of 19) and the Undergraduate applicant portal (12 of 15).

## 5 Security findings summary

The findings of *03 Technical Documentation* §5.14 (S-1 to S-18, numbered identically here so the *Notes* of §3 can cite them) merged with the security notes of every dossier's §12. Severity is this report's own judgement of likelihood × harm on a public university portal holding personal, academic and payment data: **High** — exploitable now by an outsider or by an insider against the integrity of results or money; **Medium** — needs an insider, a mis-step or a second weakness, or exposes personal data to more offices than the rule intends; **Low** — hygiene, defence in depth, or a claim that does not match the code; **Info** — recorded for completeness.

| # | Finding | Severity | Evidence | Recommendation |
|---|---|---|---|---|
| S-1 | Public hostel verification is enumerable: sequential `ALC-YYYY-NNNNN`, no check token, no throttle; returns name, photograph, hall, room and bed for every non-held allocation | **High** | `verify/VerifyController.java:369-394`; `SecurityConfig.java:56` | Put a check token in the QR (as receipts, exam cards and registrations do) and throttle the endpoint; until then answer only "genuine / not genuine" |
| S-2 | No rate limit on staff, student and applicant sign-in, forgot and reset, on `applicant/lookup`, on Post-UTME slip verification, on the results / exam / registration verify endpoints, or on the payment webhooks; `AUTH_THROTTLED` is a title nothing raises | **High** | `ProblemHandler.java:151`; `auth`, `studentportal`, `applicant`, `verify`, `payments` | A per-source limiter like `DocumentsController`'s on every public POST, ideally at the edge; lock-out already exists per account but not per source |
| S-3 | Held scripts: no ownership check on hold / bulk hold / withdraw; `release_held_scripts` adds a score version to a sheet at any stage, including PUBLISHED, bypassing the approval chain | **High** | `results/HeldScriptsController` (no `own` / `teaches`); `assessment.release_held_scripts` | Call `own(sheet)`; refuse a release past ENTRY and route it through a return |

## 6 Recommendations and remediation order

### 6.1 Principles

1. **Say what is true first.** Every stale text and placeholder in §4.4–§4.5 costs less to fix than the confusion it causes, and none needs a migration. Removing a false promise ("the student is told", "verified nightly", "rate-limited") is a remediation in itself.
2. **Close the loop on flows that already work.** Most of the 66 **NOT IMPLEMENTED** rows sit at the end of an implemented flow: a notice, a print, a verification page, a settings screen. These are small and high-value.
3. **Fix the guards before the menus.** Where a menu offers what a guard refuses (§4.3.1), decide the authority first — usually by adding the office to the guard under the Registry's instruction — and only then touch `menus.ts`.
4. **Never edit an applied migration.** Every schema fix goes in a new `V264__…` file; the SHA ledger stops the deploy otherwise (*02* §8, *08* §1.2).
5. **Re-run the inventories after every change** (`docs/manual/tools/`) and update this report's row before the feature is announced.
